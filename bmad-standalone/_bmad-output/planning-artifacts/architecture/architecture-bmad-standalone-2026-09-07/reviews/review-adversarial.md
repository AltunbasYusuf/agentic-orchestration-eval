# Adversarial Divergence Review — Browser Tetris Architecture Spine

## Overall verdict

The spine is unusually tight for its size — AD-3, AD-4, and AD-5 pin their respective data shapes precisely enough that I couldn't construct a genuine incompatibility around board/shape-table/queue *data representation* itself. The real seams are at the edges the ADs don't cover: how discrete input intent crosses the "only `update()` writes state" boundary, what Restart is actually required to reset, whether the spine's own FSM diagram agrees with FR-12, and whether the deferred line-clear flash can be built at all without breaking AD-1's "inline, same pass" guarantee. Several of these are not cosmetic — they produce two spine-compliant epics that genuinely do not integrate.

### Findings

- **critical** Line-clear flash cannot be built as literally described without breaking AD-1 (Deferred, cross-references AD-1) — EXPERIENCE.md's State Patterns row requires "brief flash on the cleared row(s) *before they shift out*" — i.e., the full rows must remain visible, flashing, for some duration prior to removal. AD-1 requires "Scoring, line-clear, and level-up all happen inline within the same `update` pass" as the lock that triggered them — i.e., the rows are gone (removed + shifted) in the very same tick they're detected. Two compliant-looking implementations diverge hard: (A) Core Gameplay Loop epic clears/shifts instantly per AD-1, and fakes the flash by stashing an ephemeral, render-only record (`state.flashEvent = {rows, capturedColors, expiresAt}` or similar) that `render()` draws for a few frames after the shift has already happened — technically AD-1-compliant, but only *simulates* "before they shift out" using pre-shift data. (B) A UX-driven implementation instead adds a genuine multi-tick "clearing" sub-state: lock detection marks rows as pending-clear in the same pass (compliant so far), but the actual array splice/shift is deferred to a *later* `update()` call once a flash timer elapses — this directly violates AD-1's "inline within the same update pass," yet is the more natural reading of "flash... before they shift out." The Deferred section dismisses this as "purely a render-section detail, doesn't cross AD-1's mutation boundary," which is only true for implementation (A); nothing in the spine forces (A) over (B), and the capability map doesn't even clearly assign flash-rendering to one epic (it's not HUD, preview, or an "overlay" per Session Control's remit, nor explicitly listed under Core Gameplay Loop's render duties). *Fix:* Add a rule (or amend AD-1) stating explicitly that line-clear removal/shift is always synchronous within the lock's `update` pass, and that any visual flash must be implemented as a short-lived, render-only echo of already-cleared data — never as a delay to the actual mutation.

- **high** No pinned channel for input intent crossing the "read-only" boundary (AD-1, AD-6) — AD-1 says `update(dt)` is the *only* function that writes `state`, and "the keydown handlers only read `state`." But movement (FR-2), rotation (FR-3), soft/hard drop (FR-4/5), pause (FR-11), and restart (FR-12) all originate in keydown handlers and must eventually mutate `state` (piece position, FSM transitions). The spine's own flowchart shows "Input handlers —writes intents→ Update" as a distinct box from "State," implying intents live *outside* `state` — but this is never made a Rule, only implied by a diagram. Two compliant epics can diverge: Core Gameplay Loop epic builds a level-triggered mechanism (e.g. a module-scoped `Set` of currently-held keys, polled once per `update` tick) — this suits continuous actions (move-repeat, soft-drop) but has no "just pressed" edge semantics. Session Control epic needs single-press semantics for P/R (a held P must toggle pause once, not flicker every tick) and reasonably builds a *separate*, incompatible mechanism (e.g. a module-scoped `pendingActions` array pushed by keydown, drained by `update`). Nothing forces these into one shared shape, and nothing stops a third implementer from deciding `state.input = {...}` is fine because "it's not really game state" — which would put a keydown handler in the position of writing to an object named `state`, arguably violating AD-1 under a strict reading while satisfying it under a loose one. *Fix:* Add a rule naming exactly one intent-carrying structure (e.g. "held-key booleans + a discrete one-shot action queue, both declared outside `state`, both write-only from input handlers and read/cleared-only from `update`") that both continuous and discrete actions must funnel through.

- **high** Restart's reset scope stops at board/score/level — active piece and next-queue are silently unaddressed (AD-3, AD-5, FR-12) — AD-3's rule is scoped explicitly to `state.board` ("Restart replaces this array wholesale"). FR-12's testable consequences list is exhaustive-looking and names only "the board, score (to 0), and level (to 1)." Neither AD-3 nor AD-5 (which only binds Session Control for the *preview render*, not for restart's write side) says anything about `state.activePiece` or `state.nextQueue` on restart. Two compliant implementations diverge: (A) Session Control epic treats Restart as "replay full initialization" — board, score, level, activePiece, and nextQueue (and any RNG/bag state) are all reset, and a fresh piece is spawned. (B) A stricter implementer follows the literal FR-12 checklist plus AD-3's board-only scope and resets *only* board/score/level, leaving `state.activePiece` as whatever it was at the moment of Game Over (or mid-fall, if restarting from Playing per Finding below) and `state.nextQueue` mid-sequence. The result: after Restart the board is empty but the falling piece is stale/misplaced, or worse, undefined if Game Over cleared `activePiece` to `null` and nothing re-spawns one. Both readings are defensible against the text as written. *Fix:* Add a restart rule (or extend AD-3) enumerating every field Restart must touch: board, score, level, activePiece (regenerated via a fresh spawn), and nextQueue (reseeded).

- **high** Spine's own FSM diagram omits the Playing→Playing restart edge required by FR-12 and EXPERIENCE.md — The Design Paradigm's Mermaid diagram shows exactly two `R` transitions: `GameOver --> Playing` and `Paused --> Playing`. It has no edge for restarting while already in `Playing`. But FR-12 explicitly says restart works "from either an active session or the Game Over screen" (an "active session" is the `Playing` state, per EXPERIENCE.md's own Information Architecture table), and EXPERIENCE.md's Interaction Primitives independently state "R: restart, works from Playing or Game Over." A literal implementer treating the diagram as authoritative (it sits in the paradigm-defining section, not flagged as illustrative-only) could gate the R-keydown handler to only act when `state.fsmState !== 'Playing'`, silently dropping restart-while-playing — fully consistent with the spine's diagram, but a direct FR-12 violation. Another implementer, cross-checking against the PRD/UX docs the spine itself cites as sources, correctly wires R to work from all three states. These two are not just cosmetically different — one produces a keybinding that silently does nothing in a state the other handles. *Fix:* Add the missing `Playing --> Playing: "R" (FR-12)` self-transition (or an equivalent note) to the diagram so it doesn't contradict the FR it's supposed to visualize.

- **medium** AD-2's fixed-rate accumulator is scoped to fall/soft-drop only, leaving FR-2's held-key horizontal repeat unpinned — AD-2's Rule text names exactly what the accumulator drives: "fixed-rate game logic (piece fall, soft-drop rate)." FR-2 separately requires "held keys repeating at a fixed rate" for Left/Right movement, but AD-2 never says horizontal-repeat timing must ride the same accumulator. One implementation folds horizontal repeat into the same accumulator-driven tick, inheriting AD-2's pause-freeze guarantee for free. Another implementation drives horizontal repeat off native browser key-repeat (`event.repeat`) or an independent `setInterval`, which is not part of "the accumulator" AD-2 promises to stop — FR-11's "no piece movement ... processed" while paused then has to be re-implemented as an ad hoc FSM-state check inside that separate timer/handler, a check AD-2 never requires anyone to add. If Core Gameplay Loop epic ships the accumulator-based version and Session Control epic's pause logic assumes (per AD-2's letter) that stopping "the accumulator" is sufficient to freeze all movement, a horizontal-repeat mechanism built on the other reading can keep moving the piece sideways while paused. *Fix:* Widen AD-2's Rule to state that *all* time-gated input repeat (fall, soft-drop, and horizontal move-repeat) shares the one accumulator, with no independent timer paths.

- **medium** "Stops the accumulator" doesn't pin the fate of the underlying frame-delta timestamp across the pause boundary (AD-2) — AD-2 requires that entering `Paused` "stops the accumulator itself, not just the render call." It does not say whether the rAF loop's `lastFrameTime` bookkeeping variable keeps updating every frame while paused (frozen accumulator, timestamp still tracked) or itself stops (early-return before either is touched). These read identically against the Rule text but behave very differently: if `lastFrameTime` is *not* refreshed during the paused frames, the first `dt` computed after Resume equals real wall-clock time elapsed *during the entire pause*, and if that raw `dt` is added into the accumulator before any per-frame clamping, it reintroduces exactly the "game-time elapses while paused" bug AD-2 exists to prevent — just deferred to the resume frame instead of during the pause. Whether this bug manifests depends entirely on an implementation detail AD-2 never mentions. *Fix:* Extend AD-2 to state explicitly that `lastFrameTime` must be reset (not merely left stale) on the Paused→Playing transition, so the first post-resume `dt` reflects one frame, not the pause duration.

- **medium** Row-major board orientation (top vs. bottom) is never pinned (AD-3) — AD-3 fixes `board[row][col]`, 20×10, cell contents — but never states whether `row 0` is the top of the visible board (spawn/game-over row) or the bottom (the floor pieces settle toward). Spawn logic (Core Gameplay Loop) needs this to place new pieces near the top; collision/gravity logic needs it to know which direction is "down"; render needs it to map array index to canvas Y. Since AD-3, AD-4, and render are each governed separately and could plausibly be written by different people/epics without a shared convention written down anywhere, one could index gravity as `row + 1` (row 0 = top) while another draws `canvas_y = row * cellSize` assuming row 0 = top of canvas vs. row 0 = floor with `canvas_y = (19 - row) * cellSize` — an inverted board only surfaces once spawn, collision, and render code from different sources are actually run together. *Fix:* Add one sentence to AD-3: "row 0 is the topmost row (spawn/game-over row); row 19 is the floor; gravity increments `row`."

- **low** State-field list in the Design Paradigm section omits the lines-cleared counter needed by FR-9 and the HUD (AD-1) — The Design Paradigm's enumeration of what `state` holds ("the board, the active piece, the next-piece queue, score, level, and the current FSM state") never mentions a cumulative lines-cleared count, yet FR-9 needs one to trigger level-ups every 10 lines, and EXPERIENCE.md's HUD panel independently requires a live "Lines" stat. Because this field's name/shape is never fixed, the Scoring & Progression epic (which writes it, likely as a monotonic total for level-math) and Session Control epic (which renders it in the HUD and must zero it on Restart per FR-12's "resets... immediately") could pick different shapes — a cumulative `state.lines` vs. a per-level countdown `state.linesUntilLevelUp` — producing either a broken HUD read or a broken restart reset depending on which shape the other epic assumed. *Fix:* Name the field explicitly in AD-1 or the Consistency Conventions table, e.g. `state.lines` (cumulative, monotonic, reset to 0 on Restart).
