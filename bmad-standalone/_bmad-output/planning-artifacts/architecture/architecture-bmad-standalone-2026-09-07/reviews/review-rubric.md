# Rubric Walker Review — Browser Tetris Architecture Spine

## Overall verdict

A tight, well-scoped spine: all six altitude-owned dimensions (paradigm, state ownership, data shapes, loop timing, script organization, deployment envelope) are explicitly decided or deferred with justification, every AD's Rule is concretely enforceable, and all 13 PRD FRs map to a governing AD. The one real gap is that the Deferred section wrongly assumes the line-clear flash is a pure render-detail — achieving the UX spec's "flash before rows shift out" plausibly requires touching state/timing, which no AD covers. At this fixture's stakes that's a discuss-not-block item; everything else is polish.

### Findings

- **medium** Line-clear flash timing is dismissed as a render-only Deferred item, but it isn't (§ Deferred, "Line-clear flash visual timing") — EXPERIENCE.md's State Patterns table specifies the flash happens "before they shift out," i.e., the row must remain visible-but-flashing for some duration *before* AD-3's board mutation removes it. PRD FR-1 also says the next piece spawns "immediately after the previous piece locks (and any resulting line clears resolve)," implying resolution (including any flash) gates the next spawn. Neither AD-1 (single mutator, no event bus) nor AD-2 (loop timing) says how a multi-frame visual-hold-before-mutation is supposed to work without either (a) adding a timer/sub-state that AD-1's "no event bus, all inline in one update() pass" rule doesn't obviously accommodate, or (b) clearing the row from state instantly and having render() fake a flash on data that's already gone (which contradicts "before they shift out"). Two epics (Core Gameplay Loop's lock→clear→spawn sequence and the render section) could reasonably diverge here — one delays spawn for the flash duration, another spawns instantly and skips the visible flash. *Fix:* either pull this into a real AD (e.g., "line-clear flash is decorative-only: state clears/shifts instantly, render animates a fading copy of the cleared row's pre-clear colors for N ms without gating spawn") or explicitly flag it as an open question for the level below rather than leaving it in Deferred with a rationale that doesn't hold up.

- **low** FSM diagram's "1:1" claim overstates the match to EXPERIENCE.md (§ Design Paradigm, opening paragraph) — the spine says the 3-state FSM (Playing/Paused/GameOver) maps "1:1 to EXPERIENCE.md's State Patterns," but EXPERIENCE.md's State Patterns table has 5 rows (Playing, Soft drop, Line Clear, Paused, Game Over); Soft Drop and Line Clear are in-state behavioral modes, not FSM states. This is likely intentional (the architecture correctly declines to make them separate FSM states) but the "1:1" wording is imprecise and could mislead an epic author into expecting a 5-state machine. *Fix:* reword to something like "maps onto the three durable session states in EXPERIENCE.md's table; Soft Drop and Line Clear are in-Playing behaviors, not separate FSM states."

- **low** Overlay rendering mechanism is a silent dimension (§ Structural Seed) — EXPERIENCE.md defines Pause and Game-Over overlays as components that appear "over the board" and dim it. The Structural Seed only names `<canvas id="board">` and `<div id="hud">`; it doesn't say whether the overlays are canvas-drawn (inside `render()`) or a separate DOM element toggled by state. AD-1 says `render()` is the sole state-reader that draws, so either approach is compatible with it, but which one isn't decided, and a DOM-based overlay vs. a canvas-drawn one are visibly different implementations two units could pick independently. *Fix:* a one-line addition to the Structural Seed (e.g., "overlay = DOM `<div>`, shown/hidden by `render()` per FSM state") would close this cheaply.

- **low** Held-key repeat mechanism for Move (FR-2) isn't assigned to a timing source (§ AD-2) — AD-2 explicitly ties the rAF+accumulator to "fixed-rate game logic (piece fall, soft-drop rate)" but is silent on whether Left/Right's "held keys repeating at a fixed rate" (FR-2) is driven by that same accumulator or by the browser's native keydown auto-repeat (which has inconsistent OS/browser-dependent initial delay and rate, and would conflict with FR-2's "fixed rate" requirement). Minor at this scope, but it's the same class of loop-timing decision AD-2 already governs for soft drop. *Fix:* fold horizontal-move repeat into AD-2's rule text so it's covered by the same fixed-rate mechanism as fall/soft-drop.
