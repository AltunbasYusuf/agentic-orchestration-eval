## Intent

**Problem:** There is no playable Tetris game in the project. The user wants a simple, self-contained, browser-based single-player Tetris implementation controllable with arrow keys, featuring line clearing, a live score counter, progressively increasing drop speed, and a game-over screen with the ability to restart.

**Approach:** Build a dependency-free HTML5/Canvas + vanilla JavaScript game so it can be opened directly in any browser with no build step. Represent the 10x20 playfield as a 2D array; implement the 7 standard tetrominoes (I,O,T,S,Z,J,L) with simple rotation states and a basic wall-kick (shift left/right/up by 1 cell if rotation would collide, otherwise block the rotation). Drive the game with a requestAnimationFrame loop that ticks piece descent on a drop-interval timer; the interval shrinks as the player clears lines (level increases every N lines), producing the increasing-speed behavior. Handle ArrowLeft/ArrowRight/ArrowDown for movement (with key-repeat throttling to avoid runaway input) and ArrowUp for rotation. On each piece lock, scan for full rows, remove them, shift rows above down, and award score using a lines-cleared x level formula. When a newly spawned piece immediately collides with existing blocks, stop the loop, freeze the board, and show a game-over overlay with the final score and a restart control that fully resets state.

## Boundaries & Constraints

**Always:**
- Always run entirely client-side (open index.html directly in a browser, no server/backend/database required)
- Always use a standard 10-column x 20-row playfield
- Always bind movement to ArrowLeft/ArrowRight/ArrowDown and rotation to ArrowUp exactly as requested
- Always keep the current score visible and updated in real time during play
- Always increase drop speed as the player progresses (e.g., per lines-cleared threshold), never staying static for the whole game
- Always show an explicit Game Over screen (final score + restart control) when a new piece cannot spawn, and stop the game loop at that point
- Always prevent pieces from moving/rotating into occupied cells or outside the playfield boundaries

**Never:**
- Never require external frameworks, build tooling, or a bundler to run the game (keep it a static file set)
- Never require network/internet access to play once the files are loaded
- Never allow the game loop to continue advancing after game over is triggered
- Never implement multiplayer, networking, or server-side persistence (out of scope for this single-player request)
- Never let key repeat cause the piece to skip collision checks or overlap existing blocks

## I/O & Edge-Case Matrix

| Scenario | Input/State | Expected | Error Handling |
| --- | --- | --- | --- |
| Move piece left/right within open space | Active piece with empty cells to its left/right, mid-board | Piece shifts one column in the pressed direction; board redraws immediately | N/A - straightforward valid move |
| Move or rotate piece against the wall or another block | Active piece adjacent to playfield edge or a locked block | Move/rotate is rejected (piece stays in place) or wall-kick applied if a valid nearby position exists | Collision check runs before mutating state; on failure, silently ignore the input (no crash, no overlap) |
| Soft drop with ArrowDown | Active piece with empty cell directly below | Piece descends one row per press/hold tick, faster than the automatic drop timer | If the cell below is occupied, treat as lock event instead of move |
| Single line clear | Exactly one row fully filled after a piece locks | That row is removed, all rows above shift down by one, score increases by the single-line point value * level | Row-scan runs after every lock; if no full rows, no score change |
| Multi-line clear (up to Tetris, 4 lines) | Two to four rows fully filled simultaneously after a piece locks | All full rows are removed together, remaining rows shift down correctly, bonus score awarded per standard multi-line multiplier | Clear detection must handle non-contiguous full rows without misaligning the board |
| Level-up / speed increase threshold reached | Cumulative cleared lines crosses the configured per-level threshold | Drop interval decreases (piece falls faster), level indicator updates if shown | Speed has a sane minimum floor so it never becomes unplayably instant |
| New piece spawn collides with existing stack (top-out) | Locked blocks occupy the spawn cells for the next piece | Game loop stops, board freezes, Game Over overlay renders with final score and a restart option | No further input except restart is processed once game-over state is active |
| Restart after game over | Game Over screen is visible, user activates restart | Board clears, score resets to 0, level/speed resets to initial, a new piece spawns, loop resumes | All game state variables must be reinitialized; stale timers from the previous run must be cleared to avoid double loops |
| Rapid/held key presses | User holds an arrow key down continuously | Movement repeats at a controlled, throttled rate rather than firing every animation frame | Debounce/repeat-delay logic prevents multiple moves per frame and prevents skipping collision checks |

## Open Questions

- Should a 'next piece' preview or hold-piece feature be included, or is core play (no preview) sufficient for this first version? Treated as follow-up/out of scope for this spec.
- Should the high score persist across page reloads via localStorage, or is only the current session's score needed? Assumed session-only for now.
- What exact scoring formula should be used (NES-style 40/100/300/1200 * level vs. a simpler flat per-line value)? Assumed a simple lines-cleared * level multiplier unless the user specifies the classic table.
- Is a simplified rotation system (basic 90-degree rotation with single-cell wall kick) acceptable, or is full SRS rotation with kick tables required? Assumed simplified given the 'simple' framing of the request.
- Should touch/mobile controls be added, or is keyboard-only (desktop) acceptable? Assumed keyboard-only per the explicit 'arrow key controls' requirement; mobile support noted as a follow-up.

**Acceptance Criteria:**
- Given the game is loaded in a browser, when the user presses ArrowLeft or ArrowRight, then the active piece moves one column in that direction unless blocked by the wall or a locked block
- Given the active piece is at the playfield edge, when the user presses the movement key toward the wall, then the piece does not move past the boundary and no error occurs
- Given the active piece has room to rotate, when the user presses ArrowUp, then the piece rotates to its next orientation; given rotation would overlap a wall/block with no valid kick position, then rotation is rejected and the piece stays in its current orientation
- Given the user presses and holds ArrowDown, when the cell below is empty, then the piece descends faster than the automatic drop rate until it locks or the key is released
- Given one or more rows become completely filled after a piece locks, when the lock event is processed, then those rows are removed, rows above shift down, and the score counter increases by the appropriate amount
- Given the player has cleared enough lines to cross a level threshold, when the next piece spawns, then the automatic drop interval is measurably faster than before
- Given a new piece's spawn position overlaps existing locked blocks, when the spawn check runs, then the game loop stops, all input except restart is ignored, and a Game Over screen displays the final score
- Given the Game Over screen is visible, when the user activates the restart control, then the board, score, and speed reset to initial values and a new game begins immediately
- Given no build tools are installed, when the user opens index.html directly in a modern browser, then the game loads and is fully playable with no console errors

## Review Triage Log

[patch/medium] In spawnPiece(), when the newly spawned piece already collides (game-over case), `current` is still assigned to the overlapping piece before triggerGameOver() runs. Because draw() is called unconditionally at the end of the same loop() tick that invoked lockPiece->spawnPiece, the overlapping piece gets rendered on top of locked blocks for one frame before the overlay appears. Cosmetic but sloppy; spawnPiece should avoid setting `current` (or skip drawing) once game-over is detected.
[patch/high] ArrowDown (soft drop) and Space (hard drop) responsiveness for held keys is entirely driven by the browser/OS native keyboard-repeat timing (delay + rate), which varies across OS/browser/user settings, rather than being throttled by game logic. This makes soft-drop speed and the chance of accidental repeated hard-drops inconsistent and non-deterministic across environments.
[decision_needed/medium] LINE_SCORES = [0, 100, 300, 500, 800] does not match the well-known 'classic Tetris' scoring table (40/100/300/1200) that most players/reviewers would expect from a game literally named/branded as classic Tetris scoring. Values appear arbitrarily chosen with no comment explaining the source or intent.
[defer/medium] tryRotate()'s wall-kick attempts only test horizontal column offsets (kicks = [0,-1,1,-2,2]) and never adjust row, so rotations that would only succeed with a vertical nudge (e.g., near the bottom of the well or for the I-piece against the floor) are always rejected even though standard Tetris kick tables allow vertical kicks in some cases. Undocumented, simplified kick behavior may confuse future maintainers comparing against SRS conventions.
[defer/medium] All game state (board, score, level, current piece, timers) lives as bare module-level `var`s captured by closures inside a single IIFE, with no state object or class. This makes the code hard to unit-test, hard to extend (e.g., adding pause, hold-piece, or next-piece preview), and mixes rendering/state/input concerns in one flat file.
[defer/low] `ctx = canvas.getContext('2d')` result is never checked for null before use. In the rare case getContext returns null (unsupported/exhausted context), every subsequent ctx.fillStyle/fillRect call throws an unhandled TypeError with no user-facing fallback or error message.
[defer/maybe-false] resetGame() unconditionally calls requestAnimationFrame(loop) with no guard against an already-running loop. Currently this is only reachable via the Restart button which is only clickable while the game-over overlay is visible (mitigating risk), but there's no explicit invariant/flag preventing two concurrent RAF chains if resetGame is ever invoked from another code path (e.g., a future 'New Game' hotkey), which would double-apply gravity/draw per frame.
[patch/low] tryMove() returns a boolean indicating success/failure, but the analogous tryRotate() returns nothing (undefined), so callers can't tell whether a rotation attempt succeeded. Inconsistent return-contract between two similarly named/purposed action functions.
[defer/medium] The game-over overlay is toggled purely via a CSS 'hidden' class with no aria-hidden/aria-live attributes, and focus is never moved to the Restart button when it appears, so keyboard/screen-reader users get no notification of game-over state and must tab blindly to find the restart control. The canvas itself also has no aria-label describing its purpose/content.
[patch/medium] loop() only checks `gameRunning` at entry and still calls requestAnimationFrame(loop) unconditionally at its end, even on the tick where triggerGameOver() just set gameRunning=false. That leaves one 'stale' RAF callback scheduled. If restartBtn is clicked within that ~1-frame window (or a wider window under frame jank/tab lag), resetGame() sets gameRunning=true and schedules its own new RAF chain via requestAnimationFrame(loop) while the stale callback is still pending. Because gameRunning is now true again when the stale callback fires, it does NOT return early — it proceeds and reschedules itself too. The result is two independent, permanently interleaved loop() chains both reading/writing the shared dropCounter/lastTime/board/current state, causing doubled draw() calls and an effective doubling (and, with repeated bad-timed restarts, further multiplication) of gravity speed that never self-corrects. resetGame()/loop() have no session token or cancelAnimationFrame guard to prevent this re-entrancy.
[decision_needed/medium] Spec says line-clear score must increase by 'the correct classic Tetris bonus' but doesn't define numeric values. LINE_SCORES = [0,100,300,500,800] matches the modern 'Tetris Guideline' single/double/triple/tetris table, not the original NES/classic formula (40/100/300/1200) that 'classic' more commonly refers to. Worth confirming which scoring table the spec author intended before treating current values as correct.
[defer/low] There is no lock delay: any failed downward move (via gravity tick or manual ArrowDown) immediately calls lockPiece(), giving the player zero grace period to slide/rotate a piece after it touches the stack. This is a plausible simplification and not contradicted by the given acceptance criteria, but it diverges from typical 'classic Tetris' feel implied by the game's framing and could surprise players expecting last-moment adjustments.
[defer/low] No defensive check for `canvas.getContext('2d')` returning null or `requestAnimationFrame` being unavailable. On an unsupported/very old or restrictive environment, the script would throw during initialization and fail silently (blank page, no user-facing error), rather than degrading gracefully.
[intent_gap/medium] The viewport meta tag ('width=device-width, initial-scale=1.0') signals intent to support mobile/touch devices, but the game is keyboard-only (document keydown listener) with a fixed 300x600px canvas and no responsive scaling or touch controls. On touch-only devices the game is effectively unplayable, and on narrow viewports the fixed-size board/HUD layout may overflow rather than adapt.
